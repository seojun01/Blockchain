
### 이더리움의 계정 종류 비교
- #### 이더리움 계정
	- 네트워크 상에서 상태를 보유하고 변화를 일으키는 주체
	- 외부 소유 계정(EOA)와 계약 계정(CA)의 두 가지 유형 존재
	- EOA (Externally Owned Account)
		- 이더리움 사용자를 위한 일반적인 계정 유형
		- 개인 키로 통제되고 코드를 저장할 수 없음
		- 주소와 연결하여 잔액 정보를 기록하며 이더리움을 주고 받는 거래를 위해 사용
	- CA (Contract Account)
		- EOA의 호출을 통해 활성화
		- 프로그램 코드를 저장할 수 있는 계정
		- 스마트 컨트랙트 코드에 의해 통제되는 계정
		- 담겨 있는 프로그램 코드는 EVM을 통해 실행\
- #### 계정 간 상태 변화
	- EOA
		- 다른 EOA나 CA에 메시지 전송 가능
		- EOA의 개인키를 사용해 트랜잭션을 생성하고 서명하여 네트워크에 전파
		- (EOA <-> EOA) 단순한 화폐 송금
		- (EOA <-> CA) 컨트랙트 코드를 실행시켜 다양한 기능 활성화
	- CA
		- 개인키가 없으므로 스스로 새로운 트랜잭션을 발생 시킬 수 없음
		- 자신 외 다른 CA 또는 EOA로부터 받은 트랜잭션에 응답하는 방식으로 동작
		- 외부에서 전달된 트랜잭션의 메시지가 조건을 충족하면 코드가 실행됨
		- 모든 트랜잭션의 출발점은 항상 EOA
### 이더리움 주소의 생성 방법을 이해
- #### 계정 구조
	- nonce
		- 계정에서 전송된 트랜잭션의 개수를 나타내는 카운터
		- 트랜잭션이 한 번만 처리되도록 보장
		- 스마트 계약의 경우 해당 계정이 생성한 계약의 수를 반영
	- balance
		- 해당 계정이 보유한 ETH(Wei 단위)양
		- 1 ETH = 1 * 10^18 Wei
	- codeHash
		- EVM 바이트 코드의 keccak256 해시 값이며 다른 필드와 달리 변경 불가
		- 상태 트리에서 해당 계약을 빠르게 검색하기 위한 값
		- CA는 실행 코드를 저장하며, EOA는 공백 문자를 해시하여 저장
	- storageRoot
		- 계약 계정의 저장소 전체를 대표하는 해시 값
		- 코드 내 변수의 상태가 모두 Map형 저장소에 기록되고 이들의 MPT 루트 해시가 기록
		- 계약 상태의 무결성을 효율적으로 검증
- #### 이더리움 주소
	- (CA) 배포자 주소와 논스를 해시하여 결정
	- (EOA) ECDSA 전자서명 기법의 공개키에 대한 해시 값의 마지막 20바이트만 사용
		- 비트코인의 이중 해시와 동일한 개념
### 노드 유형과 역할 별 레이어 분리를 설명
- #### 이더리움 노드 종류
	- 풀노드
		- 블록과 상태를 모두 검증하고 보관함
		- 과거 상태는 삭제(프루닝)해서 저장 공간 절약
		- 전체 네트워크의 무결성을 보장함
	- 라이트 노드
		- 최소한의 데이터만 저장함
		- 풀 노드에 의존하여 원격 검증 시행
	- 아카이브 노드
		- 풀 노드 데이터와 모든 과거 상태 기록 보관함
		- 과거 시점 조회 기능을 위해 사용함
- #### 이더리움 네트워크의 기능적 분리
	- 2022년 The merge(PoS 전환) 이후 네트워크는 두 계층을 나눠 역할을 분담함
		- 실행 계층(EL) : 트랜잭션을 실행하여 상태를 바꾸는 EVM 세계
		- 합의 계층(CL) : 검증위원이 블록 제안, 투표하여 최종성을 부여하는 세계
		- 역할에 따라 로직을 분리하여 각자 독립적으로 유지, 보수 가능
		- 이더리움 각 노드는 클라이언트를 통해 CL과 EL을 위한 프로그램을 역할에 맞춰 실행
### PoS 이후 블록 구조를 이해
- #### 이더리움 블록 정보
	- 블록 상태 정보
		- Block Height : 블록체인에서 해당 블록의 순서
		- Status : 블록이 확정되었는지 여부
		- Timestamp : 블록이 생성된 시간 (유닉스 시간)
		- Proposed On : 검증자가 제안한 슬록(12초 단위) / 에포크(32개 슬롯 묶음) 정보
	- 트랜잭션 및 인출 정보
		- Transactions : 블록에 포함된 트랜잭션 및 계약 내부 호출 개수
		- Withdrawals : 스테이킹 보상 인출 기록
	- 보상 및 수수료 정보
		- Fee Recipient : 블록 보상 수령자의 주소
		- Block Reward : 해당 블록의 검증자 보상
		- Size : 블록의 전체 데이터 크기
	- 가스 및 처리 정보
		- Gas Used : 블록 내 실제 소모 가스 총량
		- Gas Limit : 블록에서 쓸 수 있는 최대 가스 한도
		- Base Fee Per Gas : 기본 가스 단가
		- Burnt Fees : 소각된 ETH 총량 (Base fee 개념)
		- Extra Data : 블록 제안자가 임의로 넣은 데이터
	- 무결성 정보
		- Hash : 해당 블록 해시
		- Parent Hash : 직전 블록 해시
		- StateRoot : 전체 네트워크 상태 트리의 루트 해시
		- WithdrawalsRoot : 해당 블록의 PoS 검증자의 예치금 출금 내역을 담는 머클 루트 해시
		- Nonce : 채굴 난수 값 (PoS 전환 이후 0)
### 트랜잭션 유형을 설명
- #### 이더리움 트랜잭션
	- Type-0 (Legacy)
		- nonce : 발신 계정이 보낸 트랜잭션 누적 수
		- gasLimit : 해당 트랜잭션을 실행하기 위한 최대 가스량. 미사용분은 반환됨
		- gasPrice : 가스 당 지불 비용 (Wei 단위)
		- to : 해당 트랜잭션을 받는 주소, CA 생성 시에는 null
		- value : 전송할 화폐 양(Wei 단위), CA 생성시 첫 잔액으로 설정
		- Signature (V/R/S) : 트랜잭션 해시에 대한 ECDSA 서명 값
			- V : 공개키 복원 정보 (1바이트)
			- R : 서명 원소 1 (32바이트)
			- S : 서명 원소 2 (32바이트)
		- data : 스마트 계약 함수 호출을 입력 값
	- Type-2 (EIP-1559)
		- 기존 수수료 방식의 한계를 개선하기 위해 도입
			- 기존 레거시 방식은 사용자가 Gas Price를 직접 설정하는 경매방식
			- 네트워크 혼잡 시 과도한 수수료 지불과 수수료 예측의 어려움 발생
		- 기존 수수료(Base Fee)와 우선 수수료(Priority Fee)를 분리
			- 소각되는 기본 요금이 자동 조정되고 분리된 팁을 소폭만 올려서 조정
		- 최대 수수료를 설정하여 지불 금액을 제한하고 실제 지불되지 않은 금액은 반환
### 이더리움 확장성 개선을 위한 솔루션
- #### 블록체인 트릴레마
	- 탈중앙성, 확장성, 보안성 세 가지를 동시에 완벽히 달성하기 어려움
		- 이더리움은 트릴레마를 해결하기 위해 꾸준히 업데이트 진행
		- 탈중앙성과 보안성을 최대한 유지하면서 확장성을 개선하는 방향으로 발전 중
- #### 이더리움 PoS
	- 지분이 존재하는 검증자 중에서 무작위로 검증위원 선정
		- 32ETH 이상 예치 시 검증위원이 될 수 있는 후보에 포함
	- 동작
		- 매 슬롯(12초)마다 검증위원 중 무작위로 선정된 제안자가 블록을 제안 -> 서로 다른 슬롯에서 불기 발생 가능
		- 에포크(32슬롯, 약 6분)마다 검증위원들이 투표를 수행하여 블록 최종 확정
		- 체인 분기 시 LMD-CHOST 프로토콜로 메인 시퀀스를 결정
			- 검증자의 최신 투표와 가중치를 기준으로 선택
		- Casper FFG 프로토콜로 블록에 최종성 보장
- #### L2 롤업 솔루션
	- 이더리움 메인 네트워크(L1) 외부에 존재하는 네트워크(L2)에서 실행을 처리
		- L2에서 트랜잭션을 모아 압축 및 증명 -> L1에 관련 데이터를 게시
		- L1의 보안성 + L2의 처리 효율성 (확장성)
	- 롤업 유형
		- Optimistic Rollup : 올바르다 가정하고 L1에 전달하는 방식. 향후 이의 제기가 없으면 확정
		- ZK Rollup : 오류가 없음을 영지식증명으로 입증하고 L1에 빠르게 검증하는 방식
- #### 데이터 샤딩 & 블록
	- 샤딩 (Sharding)
		- 네트워크 데이터를 여러 조각(샤드)로 나눠 병렬 처리하게 만드는 기술
	- 블롭 (Blob)
		- (EIP-4844) 블록에 저렴하고 일시적인 대용량 공간을 추가
		- L2에서 롤업하여 L1에 올리는 데이터를 저장하는 공간으로 사용
		- 실행에는 관여하지 않고 데이터 가용성만 보장
